# alo-reader — Implementation Work Packages

Companion to `DESIGN.md`. That document holds every design decision; this one turns the plan into **18 standalone work packages (WPs)** written to be handed, one at a time, to a coding model for implementation. The implementing model makes **zero design decisions** — everything it needs is pinned here or in `DESIGN.md`.

Milestone map: **M1** = WP-00…WP-08 (headless reader) · **M2** = WP-09…WP-11 (daily driver) · **M3** = WP-12…WP-14 (power user) · **M4** = WP-15…WP-16 (public 1.0) · **M5** = WP-17 (public launch surface — after the tag, before sign-ups open).

---

## How to run this plan (operator instructions)

1. **One WP per session, strictly in order.** Give the model: the Shared Preamble below, the single WP brief, and `DESIGN.md`. Nothing else.
2. **One branch per WP** (`wp-03-ingest`). Review the diff yourself before merging; the review checklist is below.
3. **Done = every command in the WP's Acceptance block passes locally.** The model must run them and paste output, not claim success.
4. **Ambiguity rule:** if the model hits anything not specified, it must stop and report the question — never improvise a design decision. You answer, update this file if the answer is durable, and resume.
5. **Never let a WP grow.** Anything discovered mid-WP that isn't in scope becomes a note at the bottom of this file, not extra work in the branch.

### Per-WP review checklist (operator)
- [ ] Diff touches only the files/areas the WP lists.
- [ ] No dependencies added beyond the WP's list (`git diff` on lockfiles).
- [ ] Tests are real: they run against real Postgres, assert behavior (not mocks of the store), and fail if the feature is reverted.
- [ ] `rg -l clerk api/ | grep -v app/auth/` returns nothing (Clerk confined to auth module).
- [ ] Every new repository/store function on user data takes `user_id` as a required arg.
- [ ] Acceptance commands re-run clean on your machine, not just in the model's transcript.

## Shared Preamble (paste verbatim into every implementation session)

You are implementing one work package of alo-reader, a chronological RSS reader. `DESIGN.md` contains all design decisions; this brief contains your scope. Follow both exactly.

**Hard rules — violating any of these means the work is rejected:**
1. Implement ONLY what this work package specifies. If something is ambiguous or seems missing, STOP and ask; do not invent a solution.
2. Do not add any dependency not listed in this brief.
3. Do not modify files outside the areas this brief lists, except tiny mechanical edits it explicitly allows (e.g., registering a router in `main.py`).
4. All tests run against a **real Postgres provisioned by Testcontainers** — an ephemeral throwaway container spun up by the test session, never the developer's real/dev DB and never mocks. Always prefer Testcontainers for anything that needs a service (DB, etc.) when it can be used. (`make migrate` still targets the real dockerized Postgres; that is not a test.)
5. Nothing outside `api/app/auth/` may import or reference Clerk.
6. Every store/repository function touching user-scoped data takes `user_id: int` as a required argument.
7. Feed content is hostile input: sanitize at ingest with nh3; entry titles are plain text everywhere, never rendered or stored as HTML.
8. Entries are ordered by `id` (insertion order) descending. Never sort by `published_at`.
9. API errors always use the envelope `{"error": {"code": "...", "message": "..."}}`.
10. When done, run every command in the Acceptance block and include the real output.

**Pinned stack** — Python 3.14, managed as a `pyproject.toml` project with pip (**not** uv). The Python gates run in a container (`scripts/py.sh`, `PY_IMAGE`) rather than a host `.venv`, so no host interpreter has to match; FastAPI, uvicorn, SQLAlchemy ≥2.0 (async) + asyncpg + greenlet, Alembic, Pydantic v2 + pydantic-settings + python-dotenv, httpx, feedparser, nh3, zstandard, PyJWT[crypto], svix; pytest + pytest-asyncio + testcontainers[postgres]; ruff (lint+format), mypy. Node 24 + pnpm; React 18, TypeScript strict, Vite; react-router, @tanstack/react-query, @tanstack/react-virtual, @clerk/clerk-react, vite-plugin-pwa; Playwright; size-limit.

**Configuration** — no secret or connection string is hardcoded. Config is read from the environment (via python-dotenv loading a repo-root `.env`; real env vars win). `DATABASE_URL` is the single source of truth for the DB connection; compose supplies it (with sensible local defaults) and `.env.example` documents it.

**Repo layout** (created in WP-00; do not restructure):
```
api/app/{main.py,config.py,errors.py}   api/app/auth/    api/app/store/
api/app/routes/   api/app/ingest/   api/app/worker/   api/app/models.py
api/migrations/   api/tests/
web/src/{main.tsx,app/,api/,features/,keyboard/}   web/tests/
deploy/{docker-compose.yml,docker-compose.dev.yml,Caddyfile,Dockerfile.api,Dockerfile.caddy}
Makefile   MILESTONES.md   DESIGN.md
```
**Standard commands** (defined in WP-00, used everywhere): `make up` `make dev` `make lint` `make typecheck` `make test-api` `make test-web` `make e2e` `make migrate`.

### WP-17 · Public launch surface — 📋 PLANNED
**Depends:** WP-16 (needs the terms/privacy pages and the tag). **Read:** DESIGN.md §0.1 (public-first), §1.4 (quotas), §1.5 (deploy).

**Why this exists.** DESIGN.md §0.1 makes public multi-tenant hosting the primary target, and today an anonymous visitor gets `ClerkApp.tsx`'s signed-out branch: a centred Clerk `<SignIn />` in inline styles, no product name, no explanation, no theme, and *sign in* as the only action — which a first-time visitor cannot do. The front door of the primary deployment mode is the least finished screen in the product. 1.0 can ship without this (a self-hoster never sees it); public sign-ups cannot open without it.

**The decision that sets the cost, pinned so the implementer makes none:** the landing page is **static HTML served by Caddy at `/`**, and the SPA moves to **`/app`**. Not a React route: this is the page strangers link to from HN or Mastodon, so it needs an OG preview and a first paint that does not wait on a bundle, and nobody should download the app to read three paragraphs. Prerendering the SPA route would also work and was rejected as a permanent build-step cost for one page. The whole price of this choice is the route move, and it is paid once.

**Revision, 2026-09-17 — the landing page belongs to one auth mode, not to the product.** Operator caught this before any of it was built: a landing page exists to convert a stranger into an account, and `AUTH_MODE=none` has no accounts, no sign-up and exactly one user. Putting a marketing page in front of a self-hoster's own reader is a wall, not a front door. So the root path depends on the mode:

| | `AUTH_MODE=clerk` (public instance) | `AUTH_MODE=none` (self-host) |
| --- | --- | --- |
| `/` | the static landing page | `302` to `/app/` |
| `/app/*` | the SPA: signed out shows Clerk, signed in shows the reader | the SPA, no auth anywhere |
| the landing page | is the front door | never referenced, never linked |

**The SPA moves to `/app` in *both* modes, not only the public one.** Vite's `base` is fixed at build time, so two different roots would mean two builds and two images for one product. One basepath, one image; the self-hoster pays a single redirect at `/` and their bookmark still works.

**Mechanism, verified rather than assumed:** two Caddyfiles, and one variable picks which one is mounted — the pattern `deploy/Caddyfile.dev` already establishes.

```yaml
- ./${ALO_CADDYFILE:-Caddyfile}:/etc/caddy/Caddyfile:ro
```

`docker compose config` resolves that to `…/Caddyfile` by default and `…/Caddyfile.selfhost` when the variable is set. **The default is the public one**, because DESIGN.md §0.1 makes public hosting the primary target. The rejected alternative is recorded because it looks attractive: a single Caddyfile with `import {$ALO_ROOT_MODE:root_landing}` selecting a snippet *validates* under both values, and then does not branch correctly when actually served — `root_app` answered `200` with an empty body where a `302` was configured. It can be spiked later as a simplification; it is not pinned.

**The mismatch is self-diagnosing.** A self-hoster who sets `AUTH_MODE=none` and forgets `ALO_CADDYFILE` lands on a sign-up pitch for an instance with no sign-up. `/landing.js` already exists for the session check, so it also reads `auth_mode` from `/api/v1/config` and, when it says `none`, replaces the hero CTA with a line naming the variable to set. Two variables that must agree are a trap; a page that notices they disagree is not.

**Deliverables:**
- **`/` — the landing page.** Static, zero framework, served from the Caddy image beside the SPA. Content, all of it provable from this repo: the chronological / no-algorithm promise (DESIGN.md's own "inbox for the web" line); keyboard-driven; offline (the WP-14 PWA is real); full-text search over your own archive, with the measured number — **p95 ~35 ms at 5M entries**, from the nightly bench; **OPML import in one step**, because the switching cost is the entire battle; self-hostable on the same compose stack. Then a trust block, which is the unusual move and the one worth making: **free while in beta** with per-user quotas — never "free forever", billing is in DESIGN.md's post-1.0 backlog — and the retention policy in plain words (starred kept forever, unread never purged, read+unstarred purged after the horizon only once every subscriber has read them). One primary CTA, "Create a free account". Links to terms and privacy (WP-16).
- **The `/app` move.** `vite.config.ts` `base`; TanStack Router `basepath`; PWA `start_url`, `scope` and manifest; service-worker scope and the offline fallback; Clerk redirect/allowed URLs; `scripts/e2e.sh` and the Playwright specs; Lighthouse, which now has **two** targets (`/` for the landing, `/app/` for the app). `/api/*` is untouched. `docs/INSTALL.md` and `CHANGELOG.md` carry the URL change, because an existing self-hoster's bookmark moves.
- **`deploy/Caddyfile.selfhost`** (new) — `redir / /app/ 302`, the SPA under `/app/*`, everything else identical. The security-header block and the `/api` and `/otlp` routes live in a snippet file both Caddyfiles import, so the two cannot drift; the dev Caddyfile mirrors the self-host behaviour, with `/landing.html` still reachable for design work.
- **Session-aware CTA.** `/landing.js` — a real file, not inline, because `script-src` is `'self'` — checks for Clerk's session cookie and swaps the CTA to "Open alo-reader". A returning user must not be sent to a signup pitch.
- **The signed-out shell at `/app`.** Still reachable by bookmark, so it gets the landing's visual language: product name, one line, `styles/tokens.css`, theme toggle, legal links, sign-*up* primary.
- **Assets.** OG/Twitter card, favicon set, `<title>` and meta description, and one screenshot per theme **generated from the seeded e2e stack** rather than hand-captured, so they cannot silently go stale.
- **`QUOTA_SUBS_DEFAULT`.** `quota_subs` is currently hardcoded at row creation (`api/app/store/users.py`), so the sign-up quota cannot be changed without a code change and never reaches existing users. Make the default settable; keep the value per-row, which is what lets one account be raised later without a migration. **The default stays 300** — incoming users arrive with an OPML of 50–300 feeds, and a lower cap turns their first action into a list of `quota exceeded` lines.
- **`docs/LAUNCH.md`.** The Clerk dev → production checklist in order, because the order is forced: domain → Caddy TLS up → Clerk production instance DNS verified (CNAMEs + DKIM) → `pk_live_` + `CLERK_ISSUER` + `ALO_CLERK_ORIGIN` → webhook endpoint created → `CLERK_WEBHOOK_SECRET`. With the two traps recorded: `pk_live_` is origin-locked to your own `clerk.<domain>` and a wrong `ALO_CLERK_ORIGIN` kills login with console-only errors (the #76 failure), and **Clerk users do not transfer between instances** — `users.clerk_user_id` is unique-keyed on the Clerk subject, so dev-instance rows become orphans. Plus the launch settings that are dashboard-side, not code: bot protection on, and **restricted / waitlist sign-up for the first weeks**, which is the cheapest abuse control available and reversible in a click.

**Acceptance:** both modes proven by running them, not by reading the config. With `AUTH_MODE=none` + `ALO_CADDYFILE=Caddyfile.selfhost`: `/` answers `302` to `/app/`, the reader loads, and nothing anywhere links to the landing page. With the public pair: `curl` on `/` returns HTML carrying the title, description and OG tags with no application bundle referenced; Lighthouse on `/` ≥ 95 on all four categories; a signed-in browser at `/` sees "Open alo-reader" (e2e); the existing e2e suite passes against `/app` with paths updated and nothing else changed; PWA install and offline read still work from `/app`; the 180 kB bundle budget is unchanged, because none of this is in the bundle; every claim on the page checked against the code that implements it (retention horizon, quota number, search p95); and end to end on the real thing — sign up on the production Clerk instance, webhook creates the local user row, import a 300-feed OPML, read an article.

**Out of scope:** the interactive demo tenant (post-1.0: it needs seeded content, a reset job and its own abuse surface), pricing page, blog, newsletter capture (`form-action 'self'`, and nothing to send), i18n, competitor comparison tables.
